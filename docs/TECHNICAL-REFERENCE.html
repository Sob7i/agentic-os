Technical reference · agentic-os · compiled 2026-08-20

Agentic OS

A local dashboard that reads six repositories and reports where their state documents disagree with git — and, per project and opt-in, an execution layer that runs agents against the same repositories. One product, because an executor that trusts a stale document is the failure the dashboard exists to catch.

How to read this page

The product sets monospace for machine-verified fact and proportional type for a claim a document makes — the typographic split does the epistemic work. This page keeps that rule: anything in mono was read out of the code or out of git.

No suite counts, PR numbers or branch heads appear anywhere below. Those rot on someone else's schedule, and the project's own convention confines them to one block in docs/HANDOFF.md. Where this document would want such a number, it names the command that produces it instead.

§1

What it is, and why the two halves ship together

Two layers in one window, with a boundary between them that is enforced in code rather than described in a document.

The portfolio layer runs a session-start ritual across every watched project and renders the disagreements between what each project's documents claim and what git and GitHub actually say. It is read-only, stores nothing about the projects it watches, and its only network call is gh.

The execution layer is per project and opt-in: a repository declares itself in by carrying an agentos.yml, and an explicit button turns that file into a database row. From there the project gets tasks, agents, sessions and an inbox, and work runs in ephemeral git worktrees.

The reason they are one product: an executor can spend hours and real money pursuing a goal drafted from a twelve-day-stale document without tripping any of its own safety rails — every one of those rails measures the loop, none of them measures its premise. The portfolio layer is the check on the premise, and it is the half that already works.

§3

The portfolio layer

Collect facts, compare them against what documents claim, and never let the comparison assert more than it checked.

The check catalogue

Each check produces a CheckResult carrying a severity, a one-line headline, the claim it read verbatim, what git said instead, a confidence, and the file the claim came from. Only DC1 carries fix data — and its absence, not a disabled button, is how the interface signals that a drift has no automatic correction.

CheckFires whenSeverityConf.Fix
DC1 A document claims a merged-PR range whose upper bound trails the real frontier, or open PRs sit past it drift claim's own Yes — one integer, spliced
DC2 A "Next up" line names a PR that has already merged drift 0.6 No — deleting a plan line is editorial judgement, and this runs at a coin-flip
DC3 The state document is older than the last commit attention < 7d
drift ≥ 7d		 1.0 No — nothing in the text is wrong; the fix is authorship
DC4 Uncommitted files reach the project's own dirtyThreshold attention 1.0 No — not a claim. A working tree is a fact, not a sentence
DC5 The branch is ahead of or behind its remote attention 1.0 No — not a claim
DC6 A non-draft PR has been open ≥ 3 days with no review decision attention 1.0 No — it needs a review, not an edit
DC7 No commit for the project's own stalledAfterDays attention 1.0 No — it needs a commit
DC8 One of the seven itqan roles is not instantiated (skipped for the framework repo, which defines them) attention 1.0 No — someone has to write the missing role
Design rule

Every "No" above ships with the sentence in the last column, rendered on the card. "No fix available" with no explanation reads as a broken feature; the truth — that most drift is not a wrong string — is a better answer and is stored in NO_FIX_REASON alongside the code that decides it.

Four severities, because three would lie

A project's severity is the worst of its checks, ranked drift 3 > attention 2 > unverifiable 1 > in-sync 0 — with one override that is the whole reason the fourth state exists.

// lib/reconcile/checks.ts
if (worst === "drift") return "drift";
// No state doc and not the framework repo → nothing was verifiable.
if (!stateDocPath && !cfg.isFrameworkRepo) return "unverifiable";
return worst;

A project with no state document has made no claim, so nothing was compared against reality. Calling that "in sync" would assert a verification that never ran — the product breaking its own never-assert-without-a-check rule on its main screen. unverifiable is not a degraded green; it is a different sentence: nothing to check as against checked, and fine.

Claim extraction is high-precision only

Claims are pulled out of state documents by patterns that must match a full claim including its verb. A proximity pattern of the shape /PR #(\d+) .{0,40}? (merged|open)/ was written, tested against a real handoff document, and rejected.

Why proximity matching is prohibited

It captured "PR #5 unmerged" as merged — because merged matches as a substring of unmerged. It also paired "#24" with a merged belonging to a different clause.

Both would have shipped confident, wrong drift reports. A drift dashboard that invents drift is worse than no dashboard, because it teaches you to ignore it.

Each surviving claim keeps two representations: text, whitespace-normalised, for quoting in the interface, and raw, byte-exact with its line breaks, which is the only thing a correction is ever allowed to splice. It also keeps its character offset in the source file.

Acknowledgements expire by construction

"Mark verified" records that a human looked at a drift and accepted it. It is keyed by a claimHash built from the claim's own text and the verified frontier:

claimHash = sha256(project + ":DC1:" + claim.text + ":" + github.maxMerged).slice(0, 12)

So the acknowledgement dies the moment either side of the comparison moves. There is no expiry logic to get wrong and no way to silence a drift that has since become a different drift. It records that you looked, never what is true — storing a status there would be the second source of truth the product exists to prevent.

§4

The write path

Everything else in the portfolio layer reads. This is the one thing that writes, and it is built as if the browser were hostile.

A guard must not take its bounds from the thing it is bounding

An earlier version of guard 2 read the allowed target out of proposal.writes[0].relPath. That is circular: a proposal naming README.md had README.md allowed, and only the content hash further down stopped the write. allowedTargets() now resolves the state and lessons files from the repository's own role detection, independently of the proposal.

Corrections are computed, never generated. The no-egress invariant forbids asking a model to draft the prose, and that constraint produced the better design anyway: a one-integer splice is reviewable at a glance, which is the only thing that makes an approval gate meaningful. The gate's second button acknowledges rather than rejects — a rejection would be a stored opinion about a fact, and facts are re-derived on every load.

§5

The execution store

Eight tables in data/agentos.sqlite, opened through Node's built-in node:sqlite, migrated by PRAGMA user_version, with foreign keys on.

Every status change is two writes or none

writeTaskTransition is the only function in the codebase that writes Task.status. It updates the row and inserts the paired TaskEvent inside one transaction, so a status with no event recording who moved it cannot exist. It is also where the legality table lives — deliberately, because the most likely source of an illegal move is an agent's own MCP tool call, and this is the one place a check holds for every caller at once.

// lib/agentos/db.ts — a human may always move a card, so there is no 'human' row
const LEGAL_TRANSITIONS = {
  session: new Set(["todo>doing", "doing>review", "doing>done"]),
  system:  new Set(["doing>todo"]),
};
§6

The dispatch funnel

Work is dispatched, never picked up. There is no poller, no worker and no queue — a process that finds work and starts it is precisely the failure mode this product exists to catch, automated.

dispatch(taskId, trigger) only ever acts on a task id that something else already named. It is the only door to a session: createSession is the sole function that inserts a Session row, and one acceptance check asserts structurally that nothing outside dispatch.ts imports it — by name or through a namespace import.

The worktree

Every session runs in its own detached git worktree at $TMPDIR/agentos/<sessionId>. Distinct session ids are what guarantee two runs never share a directory.

§7

Session lifecycle

Five states, one of which exists purely so that a crashed server cannot leave a row claiming to be alive.

Pause and resume

When an agent calls inbox_ask, the turn ends: the session goes to waiting-inbox and its worktree is torn down. Answering creates a fresh worktree from the same pinned base sha and resumes the SDK conversation via the stored sdkSessionId.

The conversation resumes; the filesystem does not

Uncommitted work from the paused turn is gone. The tool's own description is what tells the agent to commit before asking — a fact about the prompt, deliberately, rather than a fact the system tries to enforce for it.

Two error paths here were found by review rather than by tests, and both are worth stating because the fix for one created the other:

  • Teardown used to run before the terminal write. A failing worktree remove therefore left the row saying running forever, with no end time and no reason. Teardown is best-effort now and the terminal write always happens — and on failure the session keeps its worktreePath, because that path is the only pointer to a directory that may still exist.
  • Keeping the path then collided on resume, since createWorktree derives the same path from the same session id. resumeSession clears it first, and otherwise fails with an error naming the path and telling you to remove it by hand.

The one capture point that survives a throw

A single-shot query() in the Agent SDK throws after yielding its error result — so the result, carrying the session id and the cost of work already done, arrives before the throw. Code that wraps the loop in a try and treats the catch as "nothing happened" discards a real session and a real charge.

// lib/agentos/runner/runner.ts — onMessage fires before run() settles, on both paths
onMessage: (message: SDKMessage) => void | Promise<void>;

ToolCall rows are written from that callback as they happen. Cost is recorded as the SDK's own figure, verbatim and labelled as an estimate; a null cost renders as "cost unknown" and never as $0.00, because a zero states a fact about spend that nothing checked.

§8

The agent's surface, and the gate across it

Two in-process MCP servers, four tools, no task id parameter anywhere, and an approval rule enforced twice on purpose.

Wire nameServerDoes
mcp__agentos__task_readagentosReads this session's task. Takes no input at all.
mcp__agentos__task_update_statusagentosMoves the card. Where the approval gate bites.
mcp__agentos__task_append_activityagentosAppends a note to the task's activity.
mcp__inbox__inbox_askinboxAsks the human a question and ends the turn. There is deliberately no inbox_send.

Each server is constructed per session, closing over that session's task id. No tool takes a task id as a parameter, so the agent has no way to name a different task to act on — the guard derives its own bounds rather than trusting an argument.

Layer 1 was one string away from being dead on arrival

canUseTool is handed the fully-qualified name mcp__agentos__task_update_status, not the bare one the server registers. A callback matching the bare name would never fire — and the test would still have passed, because layer 2 refuses on its own.

qualify() is now the single source both the gate and its test import. A test that builds its own qualified name proves nothing about whether the gate's idea of that name agrees with it.

Why the tools are named with underscores

The spec named them task.read, inbox.ask and so on. Dots register fine at the MCP layer — the server keeps them verbatim — but the Messages API's own tool-name field is ^[a-zA-Z0-9_-]{1,64}$, and nothing in the installed SDK rewrites the tool half of the pair. Because the two gate checks call the handler and the callback directly, no check in the suite crosses that boundary: the first thing to hit it would have been a real, paid dispatch.

The egress floor

An agent's tool grants are configuration. The prohibition on WebFetch and WebSearch is not — it is invariant 1's boundary, and one mistyped configuration value must not be able to widen "the model API" into "the internet". So the list lives in one file and is applied at both moments it could take effect:

at write timelib/agentos/agent-form.ts — an Agent row can never be stored claiming a grant it may not have.
at spawn timecomposeOptions() strips them from allowedTools and forces them into disallowedTools on every composed call, whatever the row says.

Neither point is redundant: a row written before the floor existed still has to be stripped at spawn, and a floor that only ran at spawn would leave the stored row lying about what the agent may reach. What was not deliberate was two copies of the list — a security boundary with two definitions is a silent second source of truth, and it was extracted into one during review.

One more mandatory literal

strictMcpConfig: true on every composed call. Without it the SDK reads the machine's own .mcp.json and user settings, so a spawned agent would silently inherit the owner's MCP servers — including authenticated ones. That is a real leak, not a style point, and a check asserts the literal.

§9

The shell and its surfaces

A mode switch with a persistent portfolio ribbon, and a drift band that appears only when this project has drifted.

RouteRenders
/The Board — every watched project, worst-first — inside the portfolio rail
/p/<slug>One project: the always-present ribbon, the conditional drift band, and either the execution tabs or an honest watched-only view
/p/<slug>/<tab>tasks · goals · inbox · sessions · costs
/p/<slug>/<tab>/<id>The session view — tool calls in order, commits, cost, and the drift the session started from
/p/<slug>/configAgents. Reached from a rail link outside the five tabs — a sixth tab would be a decision against the closed shell design
/overviewSays honestly that it is a later stage rather than rendering an empty frame

Three rules the shell's pure functions enforce

  • A degraded board shows no severities at all. Six confident glyphs sourced from a failed collector run would break the never-assert-without-a-check rule in the one component that is on screen at all times. ribbonModel returns { ok: false, reason } instead.
  • The drift band is a quotation with a link. It returns the project's own drift check verbatim and never re-derives, re-words or re-scores anything — which is what keeps it from becoming a second drift board.
  • An unknown slug is refused, never rendered blank. An empty frame reads as "nothing here yet" instead of "no such project".

The ribbon itself stays present even when nothing has drifted, and that was an amendment to the original instruction rather than a silent implementation choice: a ribbon that appears only on drift makes its own absence an unsourced claim.

Evidence lines on a card

A task card's evidence line is a discriminated union with five cases, and the register — the typeface it renders in — is a separate field, so a component that only ever reads .register still draws the distinction correctly.

CaseRegisterReads
none—Nothing at all. A todo card carries no other field — not an empty string, not a placeholder — so a check can assert the absence structurally
runningmonoA live session, named
executedmonoSession, duration, tool calls, cost, commit shas
failedmonoThe same, plus the recorded reason
hand-movedclaim"moved by hand · no session produced this"

Even a task that ran, failed and was swept back to todo shows nothing — it is back at the start, and an evidence line naming the failed attempt would describe a run this card is no longer claiming credit, or blame, for.

The one legitimate counter in the product

Open inbox questions. Everywhere else a count renders as a plain number, because a badge asserts urgency that nothing measured.

§10

Verification architecture

Five acceptance suites, discovered rather than listed, none of which is allowed to suppress another.

Two decisions the runner script exists to hold

every suite runsChaining with && meant one known failure hid another suite's checks entirely for three days, and nobody noticed until a third suite was added and also never ran. A red test that suppresses other tests converts one known failure into unknown coverage.
the exit code is a flagExit status is mod 256, so summing the suites' codes can land on zero and report a false green — the one thing a verification harness may never do.
the list is discoveredSuites come from package.json's own verify:* keys. Adding a stage is an insert, not an edit to a line another branch is also editing — this was a real merge conflict before it was a rule.

Exactly one thing may be mocked

The Runner interface. SQLite is real, git is real, the MCP servers are real in-process functions, and dispatch() is called for real. FakeRunner satisfies the interface by replaying a chosen message sequence with no model, no subprocess and no network — which is how the full cycle (create agent → create task → dispatch → the agent asks a question → a human answers → the session moves the card to review → the human approves) is proven end to end without spending anything.

That interface was required anyway so a cloud runner can be substituted later; its testability is a side effect, not the reason it exists.

The one check that costs money

A single real session against the real Agent SDK sits behind AGENTOS_REAL_SESSION=1 under a stage3:real-session script — deliberately named so that the verify:* discovery cannot pick it up. The default run can never spend money. It is also the only proof the other checks are testing something real, and it has not been run.

A recurring failure worth naming

Four separate times, a check passed for the wrong reason and review found it — in each case by deleting the guard the check supposedly covered and watching the suite stay green:

  • A test that the egress floor holds was fed an agent row that already excluded the two tools — it proved the fixture, not the behaviour. It is now checked against a hostile row that asks for both.
  • The check that createSession is only called from the funnel matched named imports only, so import * as db followed by db.createSession(...) bypassed it while the check stayed green.
  • A configuration parser was dead weight: both parsed values could be deleted and three checks stayed green.
  • A cross-project ownership guard — the only thing between a crafted request and editing another project's agent — had no coverage at all.

The practice that came out of it is standing rather than advisory: delete the guard, and if the suite stays green, the check is not testing what it claims to.

§11

Invariants, and where they were narrowed

Five rules that define the product. Each holds unchanged at the portfolio layer; three are narrowed — by a stated boundary, in a recorded decision — inside a project that has opted into an execution layer.

#At the portfolio layerInside an execution layer
1 Local-only, no egress. Everything is parsed on-machine; the only network call is gh Plus the model API and the hosts a session's environment explicitly allow-lists. Nothing else — telemetry stays forbidden.
2 Never assert without a check. Every displayed fact carries what was checked and when Unchanged.
3 Reality wins; a document is a hypothesis. Git is ground truth; state docs are last-known claims Unchanged.
4 Read-only by default; writes are gated. No file in another repo changes without a per-change approval click The gate moves from per-write to per-session — authorized once, at spawn, against a declared manifest of repos, paths and permissions.
5 No second source of truth. Every item traces to a file or to git; the dashboard stores no task, status or plan of its own The portfolio still stores nothing. A project's execution layer may — and everything it stores carries a session id and a commit sha as evidence. A status that cannot name the session that produced it is a claim, and renders as one.

The narrowing was itself gated: the invariants were scoped in a written decision rather than quietly relaxed, and the same decision requires the layer boundary to be real in code. That requirement is what §1's diagram draws.

§13

Known gaps and open gates

What is built is not the same as what has been proven, and the project keeps the two apart on purpose.

Owner gates — built, tested against fixtures, never exercised for real

no drift correctedStage 2's acceptance criterion is one real drift corrected through the dashboard. The fixture checks pass; no proposal has ever been approved. Merging the code did not clear this.
no real sessionThe one check that spawns a real session against the real SDK has never been run. It costs money and needs the network, which is why it sits outside the default run.
no hand-run cycleStage 3b's own criterion is that a human runs the full cycle by hand. It starts with adding an agentos.yml to a target repository — a write into another repo, and therefore owner-only. docs/HUMAN-TEST.md Part 7 has the exact file.
the ribbon, looked atThe one acceptance criterion that cannot be automated — whether six project names actually fit — is currently recorded as a computed estimate, not an observation, and labelled as such.

Known defects and limits

  • Stage 1's second criterion fails, and the code is right. It asserts that a particular project is green by name; that project stopped committing, so the stalled check correctly fires and the assertion fails. The test hardcoded a time-dependent fact about a live repository. Fixing it amends a product acceptance criterion, so it is logged with two readings and a recommendation rather than edited silently.
  • Restarting the dev server kills every running session — and the system reports that rather than hiding it. Surviving a restart needs a supervisor process, which is the cloud runner's problem.
  • The worktree is not a sandbox. A local process can read outside its working directory. It is stated here, in the feature map, and in the module's own header comment, so no caller can imply otherwise by accident.
  • Stage 1's suite is not hermetic — it needs a live gh — and two other suites assert its exact pass count. One reports a skip on a degraded upstream rather than a false regression; the other has the same exposure and is logged.

Deliberately not supported

Auto-discovery of projects · auto-refresh · a "fix all" button · any background write path · committing, staging, branching or pushing in a watched repo · model-generated corrections · an in-app undo (git already has one) · a reject button · proximity-matched claim extraction · sprints, burndowns or velocity · cloud sync, telemetry, accounts.

Working rules that show up in the code

  • verify-before-claim — never state something is true without running the check that would falsify it. This is the whole premise.
  • external-API-fields-are-guilty-until-verified — capture a real payload first. Applying this to the installed SDK found three errors in a document section that claimed to be verified: it had been checked against documentation rather than against the type definitions.
  • no-op runs report as no-op — "nothing needed changing" is a valid, honest result.
  • The agent never merges. Its output is a pull request; that is where its authority ends. Merging, tagging and any write into another repository are owner-only.
